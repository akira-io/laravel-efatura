# Compliance with Manual v11

This page maps the package against the "Manual Técnico da Fatura Eletrónica"
of Cabo Verde, version 11.0 (2025-03-14). Each row names a section or rule of
the Manual with its printed page (`§7.19, p.56`, or a rule code such as
`DN-SEQ, p.34`), states the requirement, names the code that implements it
(classes under `Akira\Efatura`, written as `Actions\BuildIudAction`) and the
test files under `tests/` that exercise it.

A row is a compliance claim only when its status is "Supported". A row marked
"Partial" or "Not supported" is not a claim: it says what is missing or what
the package reads differently. The package has not been certified by the DNRE
(Direção Nacional de Receitas do Estado), and passing its test suite does not
mean the platform will authorize a document.

The XML structure follows the bundled XSD of 2024-05-27 and its official
examples, listed with their checksums in `resources/official-artifacts.json`.
Where the Manual and that XSD disagree, the row says which one the package
follows.

## Not supported or partially supported

The rows above marked "Partial" or "Not supported" come from the gaps below.

- **OAuth authorization-code redirect flow.** The platform supports only the
  Authorization Code flow with PKCE (§10, p.65). The package does not run it:
  there is no redirect, callback or PKCE handling. `PlatformTransport` needs a
  `Contracts\AccessTokenProvider` or a `Contracts\RefreshTokenRepository` bound
  by the application, which must obtain the first refresh token itself (scope
  `offline_access`, p.67) and store it. The package never stores refresh tokens.
  The default `middleware` driver avoids this, because the middleware holds the
  taxpayer credentials (§11.5, p.78).
- **Contingency operation.** The package writes, validates and signs OFFLINE
  and OFF documents and renders their DFA, but only when the application passes
  an explicit emission context. Preparation without one is always ONLINE. The
  package does not detect that the platform is unreachable, does not switch to
  contingency, keeps no queue of contingency documents, does not track when they
  must be transmitted, and does not manage the contingency LED or the IUC. The
  only deadline it applies is the issue-date window of IDT-IMC-GE (7 days,
  p.35), checked against the local clock. A document whose online window passed
  must be issued in contingency, and that workflow is left to the application.
- **ICP-CV trust chain.** In repository 1 the key must be certified by a CA of
  ICP-CV (REPO-LV, p.40). The package ships no ICP-CV certificates. The loader
  checks the chain only when `efatura.certificates.ca_bundle_path` is set, and
  readiness warns when it is not set in production. `VerifyXmlSignatureAction`,
  `efatura:validate` and the validation route never verify the chain of the
  certificate in `KeyInfo`; they report `trust_chain_verified: false`. No
  revocation (CRL or OCSP) is checked anywhere.
- **No golden vectors from the authority.** The DNRE publishes the XSD, the
  catalogs and eleven example XML files (`resources/official-artifacts.json`),
  but no reference vectors for IUD generation, signatures or totals. The tests
  use the Luhn example of figure 7, the IUD of the official invoice example,
  the official examples for XSD conformance, and the signature structure of the
  examples. Signatures are checked with an independent library
  (`robrichards/xmlseclibs`), not against a signature the authority verified.
  The XML fixtures are reviewed by hand, not issued by the platform.
- **Checks only the platform can make.** The package validates formats and
  never calls a registry, so it does not verify: NIF existence and activity of
  emitter, receiver, payer, transport provider or transmitter (`EP-TID-EX`,
  `EP-AD-LE`, `EP-ATV-O`, `EP-EF-R`, `RP-TID-EX`, `PP-TID-EX`, `TSPP-TID-EX`,
  `TRANS-TTI-EX`, p.36-38 and p.56), the activity conditions of a DTE receiver
  (`DTE-RTC-SP-ATV`, `DTE-RTC-NSP-NATV`, p.36), that the emitter name matches the
  registry (§6.3.12, p.24), the software registration (`SW-C-EX`, p.45), the
  REMPE tax rule (`TAX-TTC-V`, p.42), IUD uniqueness in the platform (`ID-UK1`,
  p.33), the deferred `DN-SEQ` and `DN-FY1` checks against stored documents
  (p.34), and the self-billing rules of §10.5.1 (p.73). The one-hour public
  access to a DFE (`ID-PA`, p.33) is platform behaviour.
- **Platform resources outside issuance.** Only four operations are implemented:
  submit a DFE archive, submit an event archive, read one DFE by IUD, and
  request a self-billing authorization. The list read of DFE (`GET dfe` with
  `AuthorizedDateStart`, `IssueDirection` and the other parameters, §10.3,
  p.69-70), DFE statistics and deletion, LED management, taxpayer search,
  certificates, software, transmitters and the accountant list (table 22,
  p.65-67) are not implemented. Events have no documented read, so an event
  with an unknown outcome cannot be reconciled.
- **Readings not confirmed by the DNRE.** The NIF in the event ID is the
  transmitter's (§10.4, p.70); a self-billed document is submitted and read with
  the buyer's token; the total to pay subtracts the withholding, following the
  XSD Read Me rather than the formula of §6.3.18 (p.28); the tax of an I line
  counts toward the total to pay under LN-LTC-E (p.47); the signature uses
  `ds:` and `xades:` prefixes as the examples do, against the text of §9.2
  (p.64); `IssueTime` is required in OFF because the XSD requires it; a DVE
  requires its receiver under RP-R (p.37) although §6.3.13 (p.24) and the XSD
  make it optional; an FTE refuses
  settled payment entries; the IUC format is assumed.
- **Extension content.** Extra fields (§7.17, p.55) and extra item properties
  (`PROP-V-F`, p.44) accept any XML in the Manual. The package accepts plain
  text only and bounds their count and length.
- **Discount percentages.** §7.21 (p.58) allows five decimal places on a
  percentage discount. The package allows three, as the XSD `stPercentage`
  does, so it refuses what the schema would refuse.
