# Fiscal domain validation

Use the concrete Data class matching the document: `ElectronicInvoiceData` (FTE), `ReceiptInvoiceData` (FRE), `SalesReceiptData` (TVE), `ReceiptData` (RCE), `CreditNoteData` (NCE), `DebitNoteData` (NDE), `TransportDocumentData` (DTE), `ReturnNoteData` (DVE), or `RegistrationNoteData` (NLE). All extend the abstract `DocumentData` contract and expose `type(): DocumentType`. `from()` and `validateAndCreate()` run the same domain checks, validating the whole graph once; direct construction with `new` does not validate. A nested Data object that was itself created through `from()` or `validateAndCreate()` is not validated again inside its parent: the parent's own rules on it (document line rules, distinct identifiers, required prices and taxes) still run, while an object built with `new` is validated in full. Validation grows linearly with the number of lines. A document accepts at most 1000 lines (`Fiscal::MAX_LINES`) and 1000 references (`Fiscal::MAX_REFERENCES`); Manual 11 sets no count, so these are defensive package limits. Payload properties are readonly; nested values have their own validation.

## Staged payloads

`DocumentHeaderData` requires immutable issue date/time and a LED code. Series and document number may remain absent at this stage. Supplied values are validated without allocating a sequence, deriving an identifier, signing XML or contacting the authority. Self-billing authorization, isolated-act indication and an internal document number are explicit header fields. `DocumentFooterData` holds the optional note and typed plain-text extra fields.

`EmissionContextData` carries the emission mode, contingency, and optional transmitter identity and software. An omitted context means online date validation. Software and transmitter are required by a completed XML transmission, but may remain absent from the staged payload. This context is separate from the official header because those fields belong to `Transmission` in the XSD. Repository, version, document/event IDs, transmission completion, signature and sequence allocation belong to subsequent preparation stages.

The emission window is an issuance check, not a property of the data: `from()` and `validateAndCreate()` accept an already issued document whatever its age, and `DocumentBuilder::build()` runs `ValidateIssueDateAction` after creating the document. The check uses the PSR-20 `Psr\Clock\ClockInterface` the builder received. The default binding is a Carbon `FactoryImmutable` in `Atlantic/Cape_Verde`, so `CarbonImmutable::setTestNow()` freezes it in tests. Header date and time are interpreted as Cabo Verde wall-clock values. Only issuance instants are converted: a Carbon given as the header issue date and time, the contingency issue date and time, the event issue date-time, `issuedAt()` or the builder clock is converted to `Atlantic/Cape_Verde` before validation, so the stored property, its formatting and its comparisons all use Cabo Verde time whatever the host or `data.date_timezone` setting, and `from($data->toArray())` rebuilds the same values. Calendar fields (due, tax point, payment, delivery, period and duration dates and times) keep the Carbon's own wall-clock fields and are read as Cabo Verde values, so a date created at host midnight never shifts a day. Online emission admits the inclusive interval from 24 hours before the clock to one hour after it; contingency has the documented seven-day lower bound. No additional future cutoff is invented for contingency. Format validation follows the XSD, including required header IssueTime; the manual's OFF time exception concerns a conflicting XML shape and does not override the published schema. Contingency's own time is required for OFFLINE, and its IUC is required for OFF. Every fiscal date and date-time, in any format that carries a date, must fall on or after `Fiscal::EARLIEST_DATE` (2021-01-01) once read in Cabo Verde: the validation rule and the cast apply the same bound, so an instant given as `2021-01-01 00:30 UTC` (31 December 2020 in Cabo Verde) is rejected rather than accepted and then refused on rehydration.

RCE requires references and actual payments; rent receipts additionally require the typed rent details. FRE and TVE require actual payments; optional FTE payments use terms/accounts rather than actual payment entries. Required/forbidden sections follow the concrete type. Every emitter needs a complete Cabo Verde address and contacts under Manual section 6.3.12 (page 24), including an address code required by the current address rules. This local check does not verify the registered address against the authority. Receivers are required except DVE, TVE below 20,000 CVE, and DTE with an undetermined receiver. For DVE, the XSD's optional ReceiverParty and Manual section 6.3.13 (page 24) conflict with generic RP-R (page 37): the package accepts an omitted receiver under the former sources. Section 6.3.13 also broadly says Cabo Verde receiver fields follow emitter rules, while the document-specific RP rules and nullable schema express narrower requirements. The package applies those specific receiver rules; supplied addresses and contacts still validate as typed data. Self-billing still requires a receiver. A DTE taxpayer receiver must have a CV tax identity; an EP reference resolves to the already-validated emitter for this check. Foreign non-taxpayer identities remain accepted. This country check does not establish authority registration or activity status. Credit notes, debit notes and return notes enforce the published reason matrix and require references. DRP does not make RappelPeriod mandatory: the XSD declares it optional, and Manual 11 supplies no explicit contrary rule.

`EventData` distinguishes cancellation targets (one or more IUD strings) from an unused-number range (`EventNumberRangeData`). Ranges have explicit LED, series, document type and inclusive start/end numbers, with an optional year. This validates payload shape and identifier syntax; allocation, check-digit generation and completed event envelopes are not produced here.

## Reconciliation and source policy

The bundled 2024-05-27 XSD defines accepted structure and codes. [Manual Técnico v11](https://efatura.cv/assets/files/manual-tecnico-da-fatura-eletronica-v11.0-be67e62c7fb34552fbcc8eeea966e217.pdf), especially table 17 and sections 7.1, 7.6 and 7.8, supplies business rules. The distributed example XMLs illustrate structure; they are not assumed to be arithmetically consistent examples.

Payload compatibility rules live on each document's `documentRules()`: issue reasons from `IssueReason::allowedFor(DocumentType)`, line pricing and tax requirements from `DocumentType::requiresLinePricing()` and `requiresLineTaxes()`, and a sales receipt names its receiver once `netTotalAmount + taxTotalAmount` reaches `Fiscal::SALES_RECEIPT_IDENTIFIED_RECEIVER_AMOUNT`, with rounding and withholding left out. Checks that need the typed graph run after creation through the capability interfaces `HasTotals`, `HasTaxPointDate` and `SettlesOnIssue`. `VerifyDocumentTotalsAction::handle()` checks the supplied lines against supplied totals and returns nothing; a disagreement throws a `ValidationException` at the field that disagrees. It preserves exact decimal evidence and never mutates amounts. Money contexts with two and five decimal places are compared by amount, without binary floating point. Price extensions, net totals and line tax totals accept exact arithmetic, or the exact result rounded half up to two decimal places (the package's fiscal normalization) or to five decimal places (the XSD `stDecimal5` scale and the DECIMAL type of Manual §7.21). Five places matter because a product such as `3.33333 x 0.33333 = 1.1110988889` cannot be written at all; its only valid five-place form is `1.11110`. Percentages divide exactly, so no intermediate rounding happens before the comparison. Every decimal input carries at most 15 integer digits (`Fiscal::INTEGER_DIGITS`), checked by the validation rules, the casts and `FiscalMoney` before any multiplication. The Manual's DECIMAL type (§7.21) only bounds the five decimal places; the integer bound is a defensive package limit that keeps arbitrary-precision arithmetic on supplied evidence cheap. Tax and withholding aggregates accept the source's exact sum, the final sum rounded to two or five places, or the sum of amounts individually rounded to two places. An arbitrary numerical tolerance is not accepted. A payable discrepancy needs an explicit signed rounding amount.

Normal and charge lines add to net totals, deduction lines subtract, and informational nets do not contribute. The more specific LN-LTC-E rule says an informational line's ordinary tax contributes to payable despite table 17's general statement that informational tax is ignored. Informational IR remains excluded from withholding. IR is reported separately and withheld from the payable amount: payable is net plus ordinary tax minus withholding plus rounding, as the XSD Read Me states, with an absent withholding aggregate counting as zero. Nonzero withholding requires its aggregate as reconciliation evidence.

Line discounts are applied before the document discount. Percentage document discounts apply to all lines except deductions. For amount document discounts, the package uses each contributing normal/charge line's submitted net amount as allocation evidence: post-line-discount base minus net must be nonnegative, and these allocations must sum exactly to the document discount. It does not invent a proportional allocation. Deduction and informational lines remain unaffected by amount document discounts; rejecting an unexplained informational allocation is package handling of an unspecified allocation rule, not a claimed DNRE rule. DiscountTotalAmount follows table 17's line discounts plus deduction price extensions, so the separately represented document discount is not counted twice.

Fiscal registration, activity status, self-billing authorization validity, reference-document existence at the authority, and authorization of submitted XML are not verified locally. Alternative-currency totals and `FiscalMoney` accept the 178 uppercase codes of the XSD's ISO 4217 enumeration (`ISO_ISO3AlphaCurrencyCode_2012-08-31.xsd`), including the fund and metal codes Brick Money does not ship (`XAG`, `XAU`, `XBA`, `XBB`, `XBC`, `XBD`, `XDR`, `XPD`, `XPT`, `XSU`, `XTS`, `XUA`, `XXX`). The schema also enumerates the literal `IdR` instead of `IDR`; the catalog generator leaves it out, as node-efatura does, so both `IdR` and `IDR` are rejected. `CatalogCurrency` reads the container's `Catalogs` singleton, which the service provider hands it, so rebinding `Catalogs` changes the currencies `FiscalMoney` and `ForeignMoneyCast` accept. `CatalogCurrency::of()` rejects any other code with `money.invalid_currency`, returns Brick's ISO currency when it exists and otherwise a custom currency with numeric code 0 and five default fraction digits; neither the XSD nor the catalog defines a minor unit, and amounts always use the explicit five-place fiscal context, so the default is never used for arithmetic. Alternative-currency totals retain their typed amounts and exchange rate; this phase does not infer exchange-rate direction or perform currency conversion. Extra fields permit explicit empty text. Item extra properties require nonempty plain text under Manual section 7.2.6 (page 44), even though the XSD's `anyType` accepts an empty element structurally. Neither extension provides a raw-XML escape hatch in this phase.
