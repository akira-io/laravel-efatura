# Fiscal domain validation

Use the concrete Data class matching the document: `ElectronicInvoiceData` (FTE), `ReceiptInvoiceData` (FRE), `SalesReceiptData` (TVE), `ReceiptData` (RCE), `CreditNoteData` (NCE), `DebitNoteData` (NDE), `TransportDocumentData` (DTE), `ReturnNoteData` (DVE), or `RegistrationNoteData` (NLE). All extend the abstract `InvoiceData` contract and expose `type(): DocumentType`. `from()` and `validateAndCreate()` run the same domain checks, validating the whole graph once; direct construction with `new` does not validate. Payload properties are readonly; nested values have their own validation.

## Staged payloads

`DocumentHeaderData` requires immutable issue date/time and a LED code. Series and document number may remain absent at this stage. Supplied values are validated without allocating a sequence, deriving an identifier, signing XML or contacting the authority. Self-billing authorization, isolated-act indication and an internal document number are explicit header fields. `DocumentFooterData` holds the optional note and typed plain-text extra fields.

`EmissionContextData` carries the emission mode, contingency, and optional transmitter identity and software. An omitted context means online date validation. Software and transmitter are required by a completed XML transmission, but may remain absent from the staged payload. This context is separate from the official header because those fields belong to `Transmission` in the XSD. Repository, version, document/event IDs, transmission completion, signature and sequence allocation belong to subsequent preparation stages.

Issue date validation uses the container-bound PSR-20 `Psr\Clock\ClockInterface`. The default binding is a Carbon `FactoryImmutable` in `Atlantic/Cape_Verde`, so `CarbonImmutable::setTestNow()` freezes it in tests. Header date and time are interpreted as Cabo Verde wall-clock values. Online emission admits the inclusive interval from 24 hours before the clock to one hour after it; contingency has the documented seven-day lower bound. No additional future cutoff is invented for contingency. Format validation follows the XSD, including required header IssueTime; the manual's OFF time exception concerns a conflicting XML shape and does not override the published schema. Contingency's own time is required for OFFLINE, and its IUC is required for OFF.

RCE requires references and actual payments; rent receipts additionally require the typed rent details. FRE and TVE require actual payments; optional FTE payments use terms/accounts rather than actual payment entries. Required/forbidden sections follow the concrete type. Every emitter needs a complete Cabo Verde address and contacts under Manual section 6.3.12 (page 24), including an address code required by the current address rules. This local check does not verify the registered address against the authority. Receivers are required except DVE, TVE below 20,000 CVE, and DTE with an undetermined receiver. For DVE, the XSD's optional ReceiverParty and Manual section 6.3.13 (page 24) conflict with generic RP-R (page 37): the package accepts an omitted receiver under the former sources. Section 6.3.13 also broadly says Cabo Verde receiver fields follow emitter rules, while the document-specific RP rules and nullable schema express narrower requirements. The package applies those specific receiver rules; supplied addresses and contacts still validate as typed data. Self-billing still requires a receiver. A DTE taxpayer receiver must have a CV tax identity; an EP reference resolves to the already-validated emitter for this check. Foreign non-taxpayer identities remain accepted. This country check does not establish authority registration or activity status. Credit notes, debit notes and return notes enforce the published reason matrix and require references. DRP does not make RappelPeriod mandatory: the XSD declares it optional, and Manual 11 supplies no explicit contrary rule.

`EventData` distinguishes cancellation targets (one or more IUD strings) from an unused-number range (`EventNumberRangeData`). Ranges have explicit LED, series, document type and inclusive start/end numbers, with an optional year. This validates payload shape and identifier syntax; allocation, check-digit generation and completed event envelopes are not produced here.

## Reconciliation and source policy

The bundled 2024-05-27 XSD defines accepted structure and codes. [Manual Técnico v11](https://efatura.cv/assets/files/manual-tecnico-da-fatura-eletronica-v11.0-be67e62c7fb34552fbcc8eeea966e217.pdf), especially table 17 and sections 7.1, 7.6 and 7.8, supplies business rules. The distributed example XMLs illustrate structure; they are not assumed to be arithmetically consistent examples.

`VerifyDocumentTotalsAction::handle()` checks the supplied lines against supplied totals and returns nothing; a disagreement throws a `ValidationException` at the field that disagrees. It preserves exact decimal evidence and never mutates amounts. Money contexts with two and five decimal places are compared by amount, without binary floating point. Price extensions and net totals accept exact arithmetic or the package's half-up fiscal normalization to two decimal places. Tax and withholding aggregates accept the source's exact sum, rounded final sum, or sum of individually rounded amounts. An arbitrary numerical tolerance is not accepted. A payable discrepancy needs an explicit signed rounding amount.

Normal and charge lines add to net totals, deduction lines subtract, and informational nets do not contribute. The more specific LN-LTC-E rule says an informational line's ordinary tax contributes to payable despite table 17's general statement that informational tax is ignored. Informational IR remains excluded from withholding. IR is reported separately; the manual's payable formula is net plus ordinary tax plus rounding, without subtracting withholding. Nonzero withholding requires its aggregate as reconciliation evidence.

Line discounts are applied before the document discount. Percentage document discounts apply to all lines except deductions. For amount document discounts, the package uses each contributing normal/charge line's submitted net amount as allocation evidence: post-line-discount base minus net must be nonnegative, and these allocations must sum exactly to the document discount. It does not invent a proportional allocation. Deduction and informational lines remain unaffected by amount document discounts; rejecting an unexplained informational allocation is package handling of an unspecified allocation rule, not a claimed DNRE rule. DiscountTotalAmount follows table 17's line discounts plus deduction price extensions, so the separately represented document discount is not counted twice.

Fiscal registration, activity status, self-billing authorization validity, reference-document existence at the authority, and authorization of submitted XML are not verified locally. Alternative-currency totals retain their typed amounts and exchange rate; this phase does not infer exchange-rate direction or perform currency conversion. Extra fields permit explicit empty text. Item extra properties require nonempty plain text under Manual section 7.2.6 (page 44), even though the XSD's `anyType` accepts an empty element structurally. Neither extension provides a raw-XML escape hatch in this phase.
